## 1. Security Findings

### SEC-01 — **CRITICAL** — `is_admin` self-escalation via PostgREST direct API

**File:** `supabase/migrations/admin-setup.sql` (user UPDATE policy) + `lib/supabase/client.ts`  
**Vector:** The "users update own row" RLS policy uses `USING (id = auth.uid()) WITH CHECK (id = auth.uid())`. This allows any authenticated user to send `PATCH /rest/v1/users?id=eq.<their-id>` with body `{"is_admin": true}` using their anon-key session token. The policy permits it because `id = auth.uid()` is satisfied — there is no column-level restriction. The app-level `updateProfile` server action is safe because it only sends known fields, but nothing prevents a user from calling PostgREST directly.  
**Fix:** Add a `BEFORE UPDATE` trigger on `public.users` that forces `NEW.is_admin = OLD.is_admin` and `NEW.stripe_customer_id = OLD.stripe_customer_id` regardless of what the caller sends.  
**Effort:** 1h

---

### SEC-02 — **CRITICAL** — No HTTP security headers

**File:** `next.config.mjs` (entire file)  
**Vector:** The config contains only `images.remotePatterns`. No `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options`, `Strict-Transport-Security`, `Permissions-Policy`, or `Referrer-Policy` are set. On a site that takes payments via Stripe Checkout, `frame-ancestors 'none'` is the minimum required to prevent clickjacking. CSP would constrain XSS impact.  
**Fix:** Add an async `headers()` function returning these headers on `source: "/(.*)"`.  
**Effort:** 2h

---

### SEC-03 — **HIGH** — Unauthenticated write to `layovers` table

**File:** `app/layover/actions.ts` lines 9–56 (server action) + `app/api/v1/layovers/route.ts` lines 24–55  
**Vector:** `createLayover` reads `user?.id` and allows `user_id: null`, inserting via `createAdminClient()` (service-role) with no auth gate. Any anonymous caller can flood the `layovers` table with no cost to themselves. The API route has the same issue.  
**Fix:** If anonymous layovers are intentional, enforce strict per-IP rate limiting immediately. If auth is required, add `if (!user) redirect(...)` before the admin-client insert.  
**Effort:** 1h

---

### SEC-04 — **HIGH** — `layover_id` ownership not verified before use in booking

**File:** `app/booking/actions.ts` line ~38  
**Vector:** The `createBooking` action fetches a layover by its UUID to inherit `party_size`, but does not verify `layover.user_id = authenticatedUser.id`. An authenticated user can supply another user's `layover_id` to inherit that user's party size, potentially miscalculating the booking price (e.g. inheriting party_size=8 on a larger group discount).  
The API counterpart at `app/api/v1/bookings/route.ts` line 44 does add `.eq("user_id", user.id)` correctly, but the server action does not.  
**Fix:** Add `.eq("user_id", user.id)` to the layover fetch inside `app/booking/actions.ts`.  
**Effort:** 30 min

---

### SEC-05 — **HIGH** — Unauthenticated Mapbox quota drain

**File:** `app/api/builder/optimize/route.ts` lines 29–136  
**Vector:** `POST /api/builder/optimize` accepts a `stop_ids` array and calls Mapbox Matrix API + Directions API (billed per call) with no authentication check. An attacker can call this endpoint in a loop to exhaust the Mapbox monthly quota at zero cost.  
**Fix:** Require an auth session, or add rate limiting per IP before the Mapbox calls.  
**Effort:** 1h

---

### SEC-06 — **HIGH** — Custom-routes SELECT policy exposes all shared routes to any authenticated user

**File:** `supabase/migrations/phase8a-custom-routes.sql` — `routes_owner_or_share_read` policy  
**Vector:** The SELECT policy is `USING (user_id = auth.uid() OR share_slug IS NOT NULL OR is_admin(...))`. The `share_slug IS NOT NULL` clause exposes **every row with a share_slug to any authenticated user without needing to know the slug** — a full-table scan via PostgREST returns all shared routes including their `user_id`, `stop_ids`, `geometry_json`, and `legs_json`.  
**Fix:** Remove the `share_slug IS NOT NULL` clause from the RLS policy. Instead, look up shares exclusively through a server-side API route that validates the caller-supplied slug server-side.  
**Effort:** 2h

---

### SEC-07 — **HIGH** — No rate limiting on `/api/shop/interest` (email enumeration + spam)

**File:** `app/api/shop/interest/route.ts` lines 5–38  
**Vector:** No rate limiting. The endpoint returns `already: true` on duplicate email (unique constraint 23505), enabling enumeration of every registered waitlist email address. Additionally, the open INSERT allows unlimited fake signups flooding the `service_interest` table.  
**Fix:** (1) Return the same 200 payload regardless of duplicate. (2) Add Upstash/Vercel Edge rate limiting (e.g. 5 req/IP/hour).  
**Effort:** 2h

---

### SEC-08 — **HIGH** — Booking calendar ICS endpoint has no auth check

**File:** `app/api/booking/[id]/calendar.ics/route.ts` lines 12–67  
**Vector:** `GET /api/booking/[id]/calendar.ics` uses the service-role client with no session check. Any caller who knows (or guesses — they're v4 UUIDs) a booking ID can download the ICS containing tour name, party size, times, and pickup location.  
**Fix:** Add `requireAuth()`, verify `booking.user_id === user.id` before serving the ICS.  
**Effort:** 1h

---

### SEC-09 — **HIGH** — File upload: `source` and `slug` not allowlist-validated (path confusion)

**File:** `app/api/admin/upload-image/route.ts` lines 41–43, 119–120  
**Vector:** `source` is taken from `formData` without checking against `["tour", "addon"]`. `slug` is taken raw and only trimmed — not validated against `[a-z0-9-]`. The storage path is constructed as `` `${source}s/${dir}/${dir}-hero.webp` ``. A compromised admin account could supply `source = "../../"` or `slug = "../otherprefix"` to overwrite storage keys outside the intended prefix.  
**Fix:** Validate `source` with `if (!["tour","addon"].includes(source)) return 400`. Validate `slug` against `/^[a-z0-9][a-z0-9-]{0,59}$/`.  
**Effort:** 30 min

---

### SEC-10 — **HIGH** — Marketing emails have no unsubscribe link (GDPR + deliverability)

**Files:** `lib/email/templates/ServiceAvailable.ts`, `lib/email/send-service-available.ts`  
**Vector:** The `ServiceAvailable` template sends commercial marketing emails to the waitlist with no `List-Unsubscribe` header and no visible unsubscribe link. Under GDPR Art. 21 and the ePrivacy Directive, every commercial email must give recipients a way to opt out. Resend will suspend the sending domain if complaint rates exceed ~0.1%.  
Additionally, `sendServiceAvailableEmails` has no server-side guard against resending — it fires to every address passed in, trusting the caller to filter. A wrong caller invocation sends duplicates with no safety net.  
**Fix:** (1) Add `List-Unsubscribe` header and an unsubscribe URL to the template. (2) Add a guard inside `sendServiceAvailableEmails` that checks `notified_at IS NULL` before each send.  
**Effort:** 2h

---

### SEC-11 — **HIGH** — CRON_SECRET guard is bypassable when env var is unset

**File:** `app/api/cron/health-check/route.ts` lines 11–15  
**Vector:** The guard is `if (secret && incoming !== \`Bearer ${secret}\`)` — if `CRON_SECRET` is not set, `secret` is falsy and the condition never triggers, allowing any anonymous HTTP GET to run all health checks and modify the snapshot table.  
**Fix:** Change to `if (!secret || incoming !== \`Bearer ${secret}\`) { return 401; }`.  
**Effort:** 15 min

---

### SEC-12 — **MED** — Open redirect possible via `slug_redirects` `new_slug` column

**File:** `middleware.ts` lines 39–46 + `lib/admin/redirects.ts`  
**Vector:** `new_slug` values come from the `slug_redirects` table. The table has `CHECK (old_slug <> new_slug)` but no constraint preventing `new_slug = '//evil.com/path'`. If inserted, middleware constructs `pathname = /stops///evil.com/path`, which browsers interpret as a protocol-relative URL, creating an open redirect to an external domain.  
**Fix:** In `insertSlugRedirect()`, validate that both `oldSlug` and `newSlug` match `/^[a-z0-9][a-z0-9-]*$/` before upserting. Add the same check to the migration as a DB CHECK constraint.  
**Effort:** 30 min

---

### SEC-13 — **MED** — File upload: MIME type read from client-supplied Content-Type header

**File:** `app/api/admin/upload-image/route.ts` line 57  
**Vector:** `file.type` is the client-supplied `Content-Type` — not derived from the file's actual magic bytes. A crafted SVG/HTML/XML file with `Content-Type: image/jpeg` will pass the size check and be fed to `sharp`. While `sharp` converting to WebP provides a strong secondary defence, magic-byte verification is best practice.  
**Fix:** Use the `file-type` npm package to detect MIME from the first bytes of `inputBuffer` before the `sharp` pipeline.  
**Effort:** 1h

---

### SEC-14 — **MED** — `article.cover_url` stored without URL scheme validation

**File:** `app/admin/articles/actions.ts` line ~53  
**Vector:** `cover_url` is saved raw to the DB without checking it starts with `https://`. It is then rendered as `<img src={cover_url}>` in the admin UI. A `javascript:` URL or relative path could cause unexpected behaviour in some browser contexts.  
**Fix:** Validate `cover_url.startsWith("https://")` during form parsing.  
**Effort:** 15 min

---

### SEC-15 — **MED** — `dangerouslySetInnerHTML` in JSON-LD script tags — `</script>` injection

**File:** `components/seo/StructuredData.tsx` line 8  
**Vector:** `JSON.stringify(schemas)` is passed directly into `<script type="application/ld+json" dangerouslySetInnerHTML>`. If any DB field (tour name, description, etc.) contains `</script>`, the closing tag breaks out of the script block and can inject arbitrary HTML.  
**Fix:** Replace `JSON.stringify(schemas)` with `JSON.stringify(schemas).replace(/</g, '\\u003c')`.  
**Effort:** 30 min

---

### SEC-16 — **LOW** — `article.body_md` has no maximum length bound

**File:** `app/admin/articles/actions.ts` lines ~50–51  
**Vector:** `body_md` is validated as non-empty but has no upper bound. A multi-MB body causes OOM spikes during `marked` + `DOMPurify` parsing on the server render.  
**Fix:** Add `if (body_md.length > 50_000) return { ok: false, error: "Body too long" }`.  
**Effort:** 15 min

---

### SEC-17 — **LOW** — Markdown rendering: sanitization is correct but boundary must not be removed

**File:** `lib/markdown.ts` + `app/blog/[slug]/page.tsx` line ~104  
**Note:** The current `marked` → `DOMPurify.sanitize` chain is correct. This finding documents the invariant: if sanitization is ever removed (e.g. to support "trusted admin HTML"), it would be a CRITICAL XSS because `body_md` can contain arbitrary HTML. Do not remove `DOMPurify`.  
**Effort:** 0h (informational)

---

### SEC-18 — **LOW** — Sensitive env vars not documented; no `.env.example`

**File:** project root (missing `.env.example`)  
**Vector:** `STRIPE_SECRET_KEY`, `STRIPE_WEBHOOK_SECRET`, `RESEND_API_KEY`, `CRON_SECRET`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `NEXT_PUBLIC_MAPBOX_TOKEN`, `NEXT_PUBLIC_SITE_URL` are used by the application but not present in `.env.local` and not documented in any example file. A new developer or staging environment build fails silently — or, worse, falls back to hardcoded values.  
**Fix:** Create `.env.example` with all required variable names (no values). Add a `scripts/check-env.ts` prebuild assertion.  
**Effort:** 30 min

## 3. GDPR + EU Compliance

### GDPR-01 — **HIGH** — No cookie consent banner (ePrivacy Directive Art. 5(3), GDPR Art. 6(1)(a))

**Files:** `app/layout.tsx`, `components/LanguageSwitcher.tsx` line 17  
`document.cookie = 'lang=...'` fires unconditionally in `LanguageSwitcher`. The `app/layout.tsx` includes a Mapbox preconnect (`<link rel="preconnect" href="https://api.mapbox.com">`) unconditionally — this initiates a third-party network connection before any consent is given. No consent banner component exists anywhere in the codebase.  
**Fix:** Add a cookie consent banner component. Gate non-essential cookies and third-party connections until consent is given. Strictly-necessary session cookies (`sb-*`) can be exempt but must be disclosed.  
**Effort:** 4–6h

---

### GDPR-02 — **HIGH** — No self-service account deletion (GDPR Art. 17 — Right to Erasure)

**File:** `app/legal/privacy/page.tsx` line ~71  
The privacy policy states users can delete data by emailing `hello@layover-legends.com`. No self-service deletion endpoint exists. The `/account` page has no "Delete my account" button. A purely manual email process is legally permissible but will breach the 30-day SLA at scale.  
**Fix:** Add a "Delete my account" server action that: (1) deletes the `auth.users` row (Supabase cascades to `public.users`), (2) deletes `service_interest` rows by email, (3) anonymises `analytics_events` and `bookings` per retention policy.  
**Effort:** 4h

---

### GDPR-03 — **HIGH** — Consent model is legally invalid (GDPR Art. 7, Recital 32)

**File:** `app/auth/callback/route.ts` lines 15–23  
`gdpr_accepted_at` is stamped at OAuth callback with the comment "proceeding constitutes informed consent." EU supervisory authorities (including the Dutch AP) have consistently rejected "browsewrap" as valid consent for marketing communications. Additionally, `supabase/migrations/gdpr-consent.sql` lines 25–27 backfill `gdpr_accepted_at = created_at` for all existing users — this is not valid consent under GDPR Art. 7.  
**Fix:** Show an explicit opt-in checkbox (with link to Privacy Policy) on the sign-in page before Google OAuth initiates. Store the checkbox tick with a timestamp separately from the OAuth callback timestamp.  
**Effort:** 3h

---

### GDPR-04 — **MED** — `service_interest` email collection has no link to user deletion

**File:** `app/api/shop/interest/route.ts` + `app/account/export/route.ts`  
The `service_interest` table has no `user_id` FK — only a raw email string. When a user deletes their account, their waitlist entries are not cleaned up. The data export also omits `service_interest` rows from the bundle.  
**Fix:** Add a nullable `user_id` FK to `service_interest`. Include it in both the GDPR export and the deletion flow.  
**Effort:** 2h

---

### GDPR-05 — **MED** — Adult-only tours have no real age gate (Dutch content rules)

**Files:** `lib/public/featured-tours.ts` lines 22, 39 + `app/tours/[slug]/page.tsx`  
`is_adult_only` is a boolean used for sitemap exclusion and admin labelling only. Any user, regardless of age, can view and book coffee shop tours, red-light district walks, and after-dark itineraries with no age confirmation. This violates Stripe's prohibited businesses policy for adult content and potentially Dutch content regulations.  
**Fix:** On tour detail pages where `is_adult_only === true`, gate the booking CTA behind an interstitial requiring 18+ confirmation (stored in the session or a signed cookie).  
**Effort:** 2h

---

### GDPR-06 — **MED** — `service_interest` submissions have no consent checkbox (ePrivacy Directive)

**File:** `app/api/shop/interest/route.ts`  
The waitlist form collects email addresses with no explicit consent checkbox for receiving commercial emails. Sending `ServiceAvailable` marketing emails to these addresses without explicit consent violates ePrivacy.  
**Fix:** Add a required consent checkbox: "Notify me when this is available (one email only)."  
**Effort:** 1h

---

### GDPR-07 — **MED** — `marketing_opt_in` presented only post-sign-up (GDPR Art. 6(1)(a))

**File:** `app/account/page.tsx` + `app/page.tsx`  
The marketing opt-in checkbox is buried in the `/account` settings page — not presented at the point of data collection. New users who sign in via Google never see this opt-in until they visit `/account`, meaning most users are effectively opted out silently. Worse, `app/account/page.tsx` line ~47 sets `marketing_opt_in: true` as the default for a fallback profile object, meaning a user whose DB row is absent is treated as opted in.  
**Fix:** Present the opt-in checkbox on the post-sign-in welcome screen (or on the sign-in page itself). Fix the default to `false`.  
**Effort:** 2h

### GDPR-08 — **LOW** — No `/legal/cookies` page (ePrivacy Directive, Telecomwet Art. 11.7a)

**File:** `app/page.tsx` footer links  
The footer links to `/legal/privacy`, `/legal/terms`, `/legal/cancellation` but not to a `/legal/cookies` page. The privacy policy does not enumerate cookies by name, lifespan, or purpose as required by Dutch law.  
**Effort:** 2h (write the page)

## 4. Money / Stripe / Accounting

### MON-01 — **HIGH** — `automatic_tax` conflicts with `tax_behavior: "inclusive"` (VAT miscalculation)

**File:** `lib/stripe/checkout.ts` lines 79, 110, 127  
`tax_behavior: "inclusive"` is set on line items, AND `automatic_tax: { enabled: true }` is set on the checkout session (line 127). Per Stripe docs, these conflict: `automatic_tax` requires a `tax_code` on every Product (not set in `ensureProduct()` in `lib/stripe/sync.ts` line ~162). Without a `tax_code`, Stripe may silently apply 0% or override the inclusive rate based on customer location, making the VAT amount shown in `ReviewSummary.tsx` inconsistent with what Stripe actually remits.  
**Fix:** Either (a) disable `automatic_tax` and rely on `tax_behavior: "inclusive"` + stored `vat_rate`, or (b) set `tax_code: "txcd_90020001"` on every Stripe Product creation and configure Stripe Tax with the business NL address.  
**Effort:** 2h

---

### MON-02 — **HIGH** — No admin refund endpoint — cancellations do not trigger Stripe refunds

**File:** `app/booking/[id]/actions.ts` lines ~27–36  
`cancelBooking` sets `status = 'cancelled'` in the DB but does **not** call `stripe.refunds.create()`. The cancellation policy page (`/legal/cancellation`) promises "100% refund" for cancellations within the window, but the code cannot honour this automatically. A human must manually issue the refund in the Stripe Dashboard. If forgotten, the user is charged and not refunded.  
**Fix:** Add a `createRefund(bookingId)` server action that calls `stripe.refunds.create({ payment_intent: booking.stripe_payment_intent_id })` and add a "Refund" button to the admin bookings page.  
**Effort:** 3h

---

### MON-03 — **HIGH** — No capacity lock — overbooking possible

**Files:** `app/booking/actions.ts` + `supabase/migrations/booking-primitives.sql`  
The `createBooking` action inserts a new booking row unconditionally with no `SELECT FOR UPDATE` on a capacity counter and no DB CHECK constraint limiting active bookings per `(tour_id, date)`. Two users booking the last seat simultaneously will both succeed. The `bookings.md` scaffold comment line 33 acknowledges this ("Always check capacity inside a transaction") but it is not implemented.  
**Fix:** Add a Postgres function that atomically checks capacity before inserting a booking (use `SELECT … FOR UPDATE` on a `tour_capacity` counter or a partial unique index). Call it from the server action.  
**Effort:** 4h

---

### MON-04 — **MED** — Base tour price not snapshotted on booking row

**File:** `lib/stripe/checkout.ts` lines 56–82 + `app/booking/actions.ts`  
When building the Stripe Checkout line items, `tour.price_cents` is read live from the DB. If an admin changes the price after the user has seen the review page but before clicking "Pay," the Stripe session reflects the new price — the user sees a different amount than they agreed to. `booking_addons` correctly snapshots `unit_price_cents`, but the tour base price is not.  
**Fix:** Snapshot `base_price_cents` on the booking row at creation time; use that snapshot in `createCheckoutSession`.  
**Effort:** 2h

---

### MON-05 — **MED** — No VAT-breakdown accounting export

**File:** `app/admin/bookings/page.tsx`  
The admin bookings page shows gross `totalRevenueCents` with no VAT breakdown. Dutch businesses must file quarterly VAT returns with the Belastingdienst (BTW). There is no way to extract "total 21% VAT collected" or "total 9% VAT collected" from the system.  
**Fix:** Add `GET /api/admin/bookings/export.csv` with columns: date, booking_ref, net_amount, vat_rate, vat_amount, gross_amount.  
**Effort:** 3h

---

### MON-06 — **MED** — No test-mode vs live-mode guard on webhook handler

**File:** `app/api/stripe/webhook/route.ts`  
The handler records `livemode: event.livemode` but does not reject events where `livemode` mismatches the expected environment. A test webhook pointed at the production endpoint would flip production bookings to `paid`.  
**Fix:** Add `if (process.env.NODE_ENV === 'production' && !event.livemode) return new Response('wrong mode', { status: 400 })`.  
**Effort:** 30 min

---

### MON-07 — **MED** — Receipt URL never populated; users receive no Stripe receipt link

**File:** `lib/stripe/webhook.ts` line ~45 + `app/booking/[id]/success/page.tsx`  
`receipt_url` is set to `null` on booking creation. The success page renders a "View receipt" link only when `booking.receipt_url` is populated — so users never see one. Stripe automatic receipts are not enabled (no `payment_intent_data: { receipt_email }` in checkout creation).  
**Fix:** Pass `payment_intent_data: { receipt_email: userEmail }` to the checkout session. Capture `receipt_url` in a `charge.succeeded` webhook handler.  
**Effort:** 2h

---

### MON-08 — **LOW** — Double-booking prevention absent (user opens two tabs)

**File:** `app/booking/actions.ts` + `supabase/migrations/phase8c-stripe.sql`  
No partial unique index on `(user_id, tour_id)` for active statuses. A user opening two browser tabs and submitting simultaneously creates two booking rows and two Stripe Checkout sessions.  
**Fix:** Add `CREATE UNIQUE INDEX bookings_user_tour_active ON bookings (user_id, tour_id) WHERE status IN ('pending_payment', 'confirmed', 'paid')`. Handle the constraint error gracefully in the action.

## 8. Race Conditions + Concurrency

### RACE-01 — **HIGH** — Overbooking: no capacity lock (see MON-03)

Two users booking the last seat simultaneously will both succeed. See MON-03.

---

### RACE-02 — **MED** — Slug redirect cycle causes infinite 301 loop

**File:** `middleware.ts` lines 31–49 + `supabase/migrations/slug-redirects.sql`  
The migration has `CHECK (old_slug <> new_slug)` to prevent direct self-loops, but has no constraint preventing a mutual cycle (`a→b`, `b→a`). The `insertSlugRedirect()` helper in `lib/admin/redirects.ts` resolves chains in one direction but does not detect cycles. If a cycle exists in `slug_redirects`, a browser hitting `/tours/a` gets redirected to `/tours/b`, which gets redirected back to `/tours/a`, repeating until the browser's redirect limit (ERR_TOO_MANY_REDIRECTS).  
**Fix:** In `scripts/build-redirects.ts`, add a cycle-detection pass after fetching data (DFS on the redirect graph); log a warning and omit cyclic entries from the JSON. Add a DB-level trigger or application check to prevent inserting a new redirect whose `new_slug` already exists as an `old_slug` in the same entity namespace.  
**Effort:** 2h

---

### RACE-03 — **MED** — `stripe_session_id` write race with webhook on session expiry

**File:** `lib/stripe/webhook.ts` `handleCheckoutExpired()` line ~71  
The expiry handler filters by both `id = bookingId` AND `stripe_session_id = session.id`. But `stripe_session_id` is written to the booking **after** the Stripe session is created (in `checkout.ts` lines ~139–144). If the checkout.session.expired webhook arrives in the microseconds between session creation and the DB update, the handler finds no match and the booking is never reset to `draft`, leaving it permanently in `pending_payment`.  
**Fix:** Make the expiry handler filter only on `id = bookingId` (or also accept `stripe_session_id IS NULL`), then validate `stripe_session_id` matches before updating status.  
**Effort:** 1h

---

### RACE-04 — **MED** — Re-payment after back-navigation: orphaned Stripe sessions

**File:** `app/actions/checkout.ts` lines ~39–45  
Every call to `redirectToCheckout()` creates a new Stripe Checkout session and overwrites `stripe_session_id` on the booking row. If the user hits back and re-submits, the old session (still valid for 24h) is abandoned. If they somehow complete the old session (e.g. via bookmark), the webhook receives an event referencing a session_id that no longer matches the booking row, and the handler will silently skip it.  
**Fix:** Before creating a new session, check if the booking already has a `stripe_session_id` pointing to an unexpired session and redirect to that URL instead of creating a new one.  
**Effort:** 2h

---

### RACE-05 — **LOW** — Price change during checkout (base price not snapshotted)

See MON-04. The user sees one price on the review page; Stripe may charge a different amount if the admin changes price between page load and payment.

---

### RACE-06 — **LOW** — Stale redirect JSON between admin slug rename and next deploy

**File:** `lib/generated/redirects.json`, `scripts/build-redirects.ts`  
Admin renames a slug → `slug_redirects` is updated in the DB → old slug returns 404 until next Vercel deploy runs `prebuild`. For a pre-launch site with infrequent slug changes and frequent deploys this is acceptable, but it means slug redirects are never active in real-time.
